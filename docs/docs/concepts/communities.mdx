# Communities

A community is a cluster of related entities summarized for broad questions. The report complements source chunks and individual relations; it does not replace them as evidence.

## Why it exists

Some questions have no single chunk as an answer. "What are the main themes in this corpus?" needs a broad view. A list of every fact is too long to read.

A community report gives a compact view of one cluster through a title, summary, and findings. Retrieval can use the report to find a topic, then return the underlying entities or chunks for detail. Because an LLM can make errors in a report, treat its claims as a guide and compare them with source evidence.

## How it works

<Diagram folder="docs" name="communities" alt="Each entity relation is weighted by the chunks that support it. Leiden clustering groups the entities, and the graph keeps groups of two or more. A group with a total weight of 5 or more gets an LLM report. A smaller group gets a simple report. The graph embeds each report and stores the communities." />

*Groups with many attested relations get an LLM report. Small groups get a simple one.*

Community detection is an explicit, graph-wide operation. `Graph.add` does not run it automatically, because clustering reads the full graph and replaces the previous partition.

When you call `Graph.detect_communities`, Agentic GraphRAG weights each entity relation by the number of source chunks that support it. Unsupported relations weigh zero. Leiden clustering creates a hierarchy, but the graph keeps only level 0 of the hierarchy and groups with at least two entities.

For each group, the graph sums its internal relation weights. Groups with a total weight of at least 5 get an LLM report with a title, summary, rating, reason, and findings. Smaller groups get a simple report whose title lists the three top members and whose rating is half the internal weight, capped at 10. If the `llm` extra is not installed, the graph uses the simple report and logs a warning. If an LLM call fails, the graph uses the simple report for that batch and records one failure for each community in it.

The graph embeds each report title and summary for retrieval. Applying the result replaces the previous communities rather than merging two partitions.

[Search themes](../tools/search-themes.mdx) uses these embeddings. It matches the query against the report titles and summaries, then returns the passages that mention each community's members. It never returns the report text, because a community has no document scope and its report can describe documents outside the scope you searched.

A dry run is the default. It returns the groups without reports.

## Example

Seven short documents about early computing give three communities.

| Members | Internal weight | Report | Title |
| --- | --- | --- | --- |
| Babbage, Lovelace, London, and two machines (5) | 6.0 | LLM | Early Computing Pioneers in London |
| Hopper, Philadelphia, UNIVAC compiler (3) | 3.0 | Simple | Grace Hopper, Philadelphia, UNIVAC compiler |
| Turing, Bletchley, Bombe (3) | 2.0 | Simple | Alan Turing, Bombe, Bletchley |

An LLM writes the first report, and an LLM can make mistakes. In one test run, a finding said that Ada Lovelace designed the Analytical Engine. The source text says that she wrote notes on it. Compare findings with the relations.

<details>
<summary>Design choices</summary>

Relations are weighted by chunk count, so a relation that many chunks state counts more. A relation without a source chunk cannot inflate a community.

The report type depends on internal weight, not on group size. A small group with many attested relations can matter more than a large sparse group.

Small groups get a simple report, which costs no LLM call and is the same on every run. Most groups in a large graph are small.

Only level 0 is kept. One level of groups is enough for retrieval, and it keeps the number of `Community` nodes small.

Every run rebuilds the full partition, because there is no rule for merging an old partition with a new one.

Running detection on request keeps that cost out of ordinary ingestion and lets you decide when reports need a refresh.

</details>
