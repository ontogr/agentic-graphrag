# Graph storage

Agentic GraphRAG supports Neo4j and FalkorDB. Either backend holds the graph, embeddings, native vector indexes, and full-text indexes in one database. You do not need a separate vector database.

## Choose a backend

Both backends support document ingestion and updates, entity resolution, community summaries, full-text and semantic search, hybrid retrieval, evidence and citations, and task and decision memory. The Python library, built-in agent, and MCP server use the same graph-store interface.

| Choice | Neo4j | FalkorDB |
| --- | --- | --- |
| Server | Neo4j 5.23 or later, self-hosted or Aura | FalkorDB 4.22.2 or later, with `RESULTSET_SIZE -1` |
| Python extra | `neo4j` | `falkordb` |
| Connection | Bolt protocol, `NEO4J_*` settings | Redis protocol, `FALKORDB_*` settings |
| Multi-statement writes | `run_in_transaction` commits or rolls back the callback's writes together | Statements run in order, with no rollback of earlier statements |
| Keyword ranking | Neo4j's native full-text index scores matches | Matches any query word and ranks by the number of matching terms |
| Vector metrics | Cosine and euclidean | Cosine and euclidean |
| Node-distance reranking | Shortest-path distance | Shortest-path distance up to five relationships |

Use Neo4j when you need rollback across a multi-statement write or already operate Neo4j or Aura. Use FalkorDB when you want a Redis-protocol graph server and can account for its partial-write behavior. Identical search requests can return different rankings because the native indexes differ.

[Configure storage backends](../guides/configure-storage-backends.mdx) to install a driver, start a server, and connect from Python or MCP. Changing the selected backend connects to a different database. It does not move an existing graph or its indexes.

## Why it exists

A graph and a vector index answer different questions. The graph stores relations and provenance, while a vector index finds text or entities that are semantically close to a query. Retrieval can combine the initial matches with graph context when its recipe requests a walk.

Keeping both in the selected graph store means graph records and vectors share one database, but an ingestion call is not one transaction. A cutover job stages writes and makes them visible at commit. Search reads graph data and vectors from the same database. FalkorDB's [commit recovery and retry limits](../guides/configure-storage-backends.mdx#falkordb-behavior-to-know) still apply.

## How it works

1. Write. `Graph.add` writes documents with their sections, tables and figures, chunks, entities, and relations to the selected store. It also writes an embedding onto each entity, resolved entity, community, and chunk node.
2. Search. The engine uses the store's native full-text and vector indexes. Hybrid search combines both rankings.
3. Read. The engine reads the full items back from the store and walks the graph when the recipe asks for it.

## The store

| Holds | Searches |
|---|---|
| Source-file records, documents, sections, tables, figures, chunks, entities, resolved entities, relations, communities, tasks, events, decisions, and indexes | Full-text, dense vector, and hybrid search, graph walks, and read-only graph queries |

The database stores source-file records and extracted content, not a backup of the original files. Keep the original files separately.

## Embedders

An embedder turns text into a vector. The default embedder runs a FastEmbed model on your machine. The default model produces 384 values per text.

`Graph.open` compares the embedder's dimension with the store's vector indexes. It raises an error when they differ, before it writes any vector. Use the same embedding model for ingestion and retrieval.
