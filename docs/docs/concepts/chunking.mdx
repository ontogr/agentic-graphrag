# Chunking

Chunking divides a document into pieces that extraction and search can process. Each chunk keeps its source location and section context, so smaller search units remain traceable to the original document.

## Why it exists

Search and extraction work on short pieces of text. Where you cut decides what they can find. A cut in the wrong place can separate a name from the fact about it.

A document already has structure: headings, paragraphs, and tables. The chunker uses that structure to avoid cutting facts apart where possible, while keeping chunks small enough for search and extraction. Larger chunks keep more context and make search less precise. The default `size` is 600 tokens, and the default `min_size` is 150 tokens.

## How it works

<Diagram folder="docs" name="chunking" alt="With a size of 600 tokens and a min_size of 150, a short first section carries on into the next section, so the two share one chunk. A table never mixes with text and becomes row groups that each repeat the header row. A paragraph over the size is cut at sentence boundaries." />

*An example with the default size of 600 tokens and a min_size of 150.*

1. Pack. The chunker walks the sections in reading order. A unit is a paragraph, list, code block or formula. The chunker adds units to a chunk until the next unit would pass `size` tokens. The default size is 600 tokens. The chunker does this packing itself, without Chonkie.
2. Split. A unit that is over `size` on its own is cut at paragraph, sentence, clause or word boundaries. The cut is made by the [Chonkie](https://github.com/chonkie-inc/chonkie) RecursiveChunker, and the chunker calls it only for a unit or heading that is longer than `size`.
3. Merge. When a section ends and the open chunk has fewer than `min_size` tokens, the chunk carries on into the next section. The default `min_size` is a quarter of `size`. The next heading goes into the chunk text, so the text keeps its meaning.
4. Tables. A table never mixes with text. If its rendered text exceeds `size` and it has more than one body row, it becomes row groups. Each group repeats the header row, and only the first group includes the caption. A table with zero or one body row stays one chunk, even if it exceeds `size`.

One `Chunker` serves every format. Each loader maps its source into sections and units first, so chunk behavior does not depend on a file extension. [Docling](https://github.com/docling-project/docling) does not chunk. Its loaders return sections and units, and the chunker makes every chunk.

### What a chunk carries

- Location: text provenance gives a character range in the normalized document text. The range covers source units, so chunk text can also include headings and blank-line separators. Page-based provenance keeps page numbers and boxes supplied by the loader. A table that stays in one chunk keeps its page spans; split row groups have no page spans.
- Headings: a chunk keeps the headings above it in `heading_path`.
- Sections: a chunk lists the sections whose text it holds in `section_ids`. In the graph it sits under the lowest section that holds all of that text. A table chunk sits under its table.
- Origin: a chunk records the name of the chunker and a fingerprint of its settings.
- Identity: a chunk id comes from the document, its version, the chunker fingerprint and the chunk number. A new version or new settings give new ids.

### Record rows and chat

A record row, such as one CSV row, has no sections. Its text is one unit, split into multiple chunks if it exceeds `size`. A chat file has one section for each message. A window of short messages can share one chunk.

## Example

A report has a section "Results" with three short paragraphs and a table. The chunker packs the three paragraphs into one chunk of about 300 tokens. The table becomes its own chunk, with the header row first. A search for a figure in the table returns the table chunk. The agent can then read the section "Results" through the graph.

Suppose you change `size` from 600 to 400 and call `Graph.update` for the file. Agentic GraphRAG chunks it again, even though the text did not change. The settings fingerprint changed, so the chunk ids change.

The fingerprint also covers the version of the splitter and a number for the table rendering rules, so an upgrade that changes chunks makes `Graph.update` chunk again.

<details>
<summary>Design choices</summary>

One chunker serves all formats. Every loader gives the same input: sections made of units. A single packer then behaves the same for every format. A per-format choice would also make loading harder to predict.

There is one level of chunk. Extraction and search use the same piece. The agent can get wider context by walking from the chunk to its section in the graph. A second, larger level could add context, but it would also require another set of embeddings.

The default size is 600 tokens. Treat the default as a starting point and evaluate chunk sizes on your own documents and questions.

A small chunk carries on into the next section. Sections that hold a line or two make chunks that embed badly and cost an extraction call each. Carrying on removes most of them.

Each chunk records its chunker. `Graph.update` compares its fingerprint with the current one. If the settings changed, the document is chunked again even when its text did not change.

</details>
