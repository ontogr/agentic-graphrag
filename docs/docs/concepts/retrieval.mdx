# Retrieval

Retrieval finds the parts of your documents that answer a question, and it lets an answer point back to the exact text it came from. Agentic GraphRAG has two ways to do this. The evidence tools in `agrag.evidence` search your documents, return the exact text of a passage, and check the citations in an answer. The built-in agent and the MCP server use them. `SearchEngine` runs recipes that return ranked results as data, without citations.

No single search finds everything. A name lookup finds "Ada Lovelace" and misses "the main themes in this corpus". A keyword search finds an exact contract term and misses a paraphrase of it. A vector search finds the paraphrase and can rank a similar but wrong passage first. The tools below cover these cases one at a time.

## How a question becomes a cited answer

An answer is built only from passages that the system read, and each claim in it points to the passage it came from. To see how, follow one question through the three steps, using the notes in [Set up the example](../tools/example-setup.mdx). The question is "How soon is customer data erased?". The output blocks on this page come from a real run, and your ids differ.

### Step 1. Search

A search returns the best matches as short previews. This is the output of a hybrid [passage search](../tools/passage-search.mdx) for the question:

```text
ok
0.0328  ev1:c:f24b301d...d7c4d6ef  ['lexical', 'semantic']
    Data retention  Robot logs are kept for 30 days and then deleted. A cu
0.0320  ev1:c:f24b301d...3e66aa77  ['lexical', 'semantic']
    Acme Robotics engineering notes  Route planning  Maria Chen works for
0.0161  ev1:c:f24b301d...12cd16fb  ['semantic']
    | Component | Owner | Purpose | | --- | --- | --- | | Orion Planner |
```

Each pair of lines is one match. The number is a score that puts the matches in order. The text under it is a preview of the first characters of the passage. The id on the first line is an evidence id. It points to one passage in one version of one document, so it keeps pointing to the same text after the document changes. The first match looks right, but a preview can stop before the sentence you need.

### Step 2. Read

[Fetch evidence](../tools/fetch-evidence.mdx) takes an id and returns the whole passage:

```text
ok current Acme Robotics engineering notes
Data retention

Robot logs are kept for 30 days and then deleted. A customer can ask Acme Robotics to erase their delivery data. After the request is verified, the data is deleted within 10 business days.
```

The first line has three parts. `ok` is the status of the fetch, and it means the text is complete. `current` is the version of the document, and it means the document has not changed since this id was made. After an edit, the old id returns the old text marked `superseded`. The last part is the document title, and the passage follows on the next lines.

The passage answers the question: the data is deleted within 10 business days. Only text read this way can be cited.

### Step 3. Answer and check

The answer cites the id in square brackets. [Check citations](../tools/check-citations.mdx) compares each cited id with the ids that were read. Here the answer cites three ids, and only the first was read:

```text
ev1:c:f24b301d...d7c4d6ef    valid
ev1:c:f24b301d...12cd16fb    not_fetched
ev1:c:oops                   malformed
```

The second id points to a real passage that nobody read. The third is not an id at all. A `valid` verdict shows that the passage was read. It does not show that the passage supports the claim. A valid citation then becomes a numbered reference:

```text
Customer data is deleted within 10 business days. [1]

### Sources

[1] Acme Robotics engineering notes
```

### Choose which documents can be read

You give the tools a list of documents that they may read. The list is called the scope. The tools never read outside it, and the model cannot change it. An id from a document outside the scope behaves as if the document does not exist.

## Retrieval strategies

### Keyword search

Keyword search matches the words of the query against chunk text with a full-text index. [Passage search](../tools/passage-search.mdx) runs it in `lexical` mode.

Main features:

- Finds exact words, identifiers, defined terms, and names.
- Does not find synonyms or paraphrases.
- Treats the query as plain words. Quotes, `AND`, and `-` have no effect.

### Semantic search

Semantic search embeds the query and finds the chunks with the nearest embeddings. [Passage search](../tools/passage-search.mdx) runs it in `semantic` mode.

Main features:

- Finds a passage that says the same thing in different words.
- Always returns the nearest chunks, even when none of them answers the question.
- Needs the same embedding model that ingestion used.

### Hybrid search

Hybrid search runs keyword search and semantic search, then fuses the two ranked lists with reciprocal rank fusion. It is the default mode of [passage search](../tools/passage-search.mdx).

Main features:

- Keeps the hits that either search finds.
- Ranks a chunk higher when both searches rank it well.
- Reports `partial` when one of the two searches fails.

### Entity search

[Entity search](../tools/entity-search.mdx) finds the things your schema names, such as people, contracts, or products, by name or by meaning. Each entity comes with up to three passages that mention it.

Main features:

- Finds an entity even when the question spells its name differently.
- Returns only entities that extraction created and that a passage in scope mentions.
- Marks an entity `unsupported` when none of its passages is current.

### Relationship exploration

[Relationship exploration](../tools/explore-relationships.mdx) follows the stored relations around one entity, up to two steps.

Main features:

- Marks each relation as an assertion that a passage states, or as a path that no passage states.
- Lists the passages that state an assertion, so you can fetch and cite them.
- Reports the bound that cut the walk.

### Document tree navigation

[Document tree navigation](../tools/navigate-document-tree.mdx) reads the passages near a passage you already have, using the section structure and the reading order of the document.

Main features:

- Reaches the section, the sibling sections, the other passages in a section, the previous or next passage, and the rows around a table cell.
- Reads only the document version of the passage you start from.
- Starts from an evidence id, so it cannot search.

### Recipe search

[Recipe search](../tools/recipe-search.mdx) runs entity, chunk, and community search at the same time and returns ranked results as data.

Main features:

- Fuses the lists, and can walk the graph and re-rank.
- Returns entities, passages, and community reports.
- Has no document scope and no citation support.

## Which tool to call for a question

| The question | Start with | Then |
|---|---|---|
| Contains an exact word, a code, a defined term, or a quoted phrase | `search_evidence` in `lexical` mode | Read the best hits with `fetch_evidence`. |
| Describes an idea in words the document may not use | `search_evidence` in `semantic` mode | Read the passages you will use with `fetch_evidence`. |
| Fits neither case, or you are unsure | `search_evidence` in `hybrid` mode, the default | Read the hits you will quote with `fetch_evidence`. |
| Names a thing and asks about its relations ("who worked with Babbage") | `entity_search` | `explore_relationships` from the best entity, then read the passages on its assertion edges with `fetch_evidence`. |
| Needs the section, the table, or the text around a passage you already have | `navigate_document_tree` from that passage's id | Read the neighbors you cite with `fetch_evidence`. |
| Asks for the main themes of a corpus | `SearchEngine` with the `THEMATIC` recipe | Read the community reports. |

The table uses the tool names of the built-in agent and the MCP server. The Python functions in `agrag.evidence` have the same names.

Passage search belongs in every sequence that ends in a citation. Entity search depends on extraction, so a fact that extraction missed has no entity, and passage search still finds it because it reads the stored text.

## Rules for every evidence tool

- A search finds only the current version of each document. Fetch and navigation can still read an older version, and they label it `superseded`.
- Every tool limits how many results and how much text it returns. A result says `truncated` when the limit cut it short.
- A failed search says so. If one half of a hybrid search fails, the status is `partial` and the result names the failed half. An empty list means that the search ran and found nothing.
- A score orders the matches of one call. You cannot compare scores from different modes or different tools.
- An empty result does not prove that the answer is missing. It means that no current passage matched this query.

## Where you can use the tools

| Where | Entry point | Scope comes from |
|---|---|---|
| Python | The functions in `agrag.evidence`. | The `scope` argument of each call. |
| Built-in agent | `build_agent` registers the tools for the model. | The `scope` argument of `build_agent`. The model cannot see or change it. |
| MCP server | `agrag-mcp` registers the tools for any MCP client. | `MCP_SCOPE_DOCUMENT_KEYS`. |

All three read the same graph. Semantic and hybrid search embed the query with the embedder you pass in, and the vectors in the graph come from the embedder that ingestion used, so both must be the same model. The [tools reference](../reference/tools.mdx#tool-names) maps each operation to its function and tool names.

<details>
<summary>Design choices</summary>

Search returns previews and not full text. A list of ten previews is short enough to scan at once, and only a fetch makes an id citable, so a fetch call read every cited passage.

The scope sits outside the model. A model that can name any document key can read any document, so the caller sets the scope when it builds the agent or starts the server and the tools apply it in the query.

Search and fetch treat versions differently. A search result reflects what the document says now. An id from an earlier run still resolves, so a citation stays checkable after the document changes, and fetch labels that text `superseded`.

</details>
