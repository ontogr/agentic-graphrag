# Features

<Diagram name="context-graph" alt="Three connected graph layers. Enterprise knowledge contains documents, sections, chunks, entities, and relations. Conversation history contains tasks, events, and steps. Decision traces link conclusions to document passages, task events, and other decisions." />

## Structure-aware ingestion

<Diagram name="document-to-graph" ext="svg" alt="A file is read by Docling into typed parts with heading levels: a title at level 0, headings at levels 1 and 2, then paragraphs, lists, tables, and figures. Agentic GraphRAG stores them as a Document, nested Sections, Tables, Figures, and Chunks joined by HAS_CHILD, with NEXT_CHUNK between neighboring chunks." />

### Loading files

- You can add a file, a folder, a pattern that matches many files, a list of paths, plain text, or documents you built yourself.
- Plain text, logs, and XML files are read by the core loaders.
- [Docling](https://github.com/docling-project/docling) reads Markdown, HTML, AsciiDoc, Word, PowerPoint, and Excel files. These formats need no model, so the base install is enough.
- PDF and image files go through Docling with its layout and table models. They need the optional `docling` install.
- Each row of a CSV or TSV file, and each record of a JSON or JSON Lines file, becomes its own document. You name the column that holds the identifier.
- A conversation file is read with one section for each message.
- Headings, sections, tables, and figures stay in the graph. PDF pages keep their page numbers and positions.
- The text encoding is detected. Byte-order marks, line endings, and Unicode forms are normalized, and you can change each of these choices.
- A failing source does not have to stop the run. You choose whether it stops the run, is skipped, or is set aside with the reason.
- A file is identified by its full path, so adding a changed file updates the document that is already stored.

See [Loading documents](../concepts/loading.mdx) and [Ingest documents](../guides/ingest-documents.mdx).

### Splitting into chunks

- Sections are packed into chunks in reading order. A small chunk carries on into the next section, so short sections do not each become a tiny chunk.
- A table that fits stays whole. A larger table is split into groups of rows that each repeat the header row, and tables never share a chunk with running text.
- A chunk records its heading path, the sections it covers, and its position as character offsets or as page positions.
- The heading path is placed in front of the chunk text when the chunk is embedded. Consecutive chunks are linked in reading order.
- Each chunk is stamped with the chunker and its settings. A document is chunked again when those settings change.

See [Chunking](../concepts/chunking.mdx) and [Configure chunking](../guides/configure-chunking.mdx).

## Schema and ontology

- You write the schema in code, in a YAML or JSON file, with Pydantic classes, or by importing an OWL or RDFS ontology.
- You can start from the default schema or a ready-made preset for operations or legal documents, then override, exclude, or add to it. A schema can also be exported to JSON Schema, SHACL, or JSON-LD.
- The schema is closed. Extraction, graph creation, retrieval, and agents read the same entity types, relation types, and allowed type pairs.

See [Ontologies](../concepts/ontologies.mdx), [Define a graph schema](../guides/define-a-graph-schema.mdx), and the [default schema](../reference/default-schema.mdx).

## Entity and relationship extraction

<Diagram name="schema-pipeline" alt="Extraction reads each chunk with a local model, sends uncertain chunks to an LLM, and checks the result against your schema. Entities and relationships outside the schema are saved for review. Resolution then compares entities in steps, from cheap checks to an LLM, and stores each match as a link." />

<Diagram name="entity-extraction" ext="svg" alt="A chunk is read by GLiNER on your machine. In hybrid mode, chunks the local model is unsure about go to an LLM through BAML, within a budget. Your schema feeds both models and the schema check. Declared results enter the graph, and results outside the schema become candidates that you review. Approval returns a schema patch." />

- You choose the mode: `gliner` runs only the local model, `hybrid` (the default) adds LLM review, and `llm` sends chunks straight to the LLM.
- A local model reads every chunk and finds entities and relations on your machine, so a graph can be built without an LLM key.
- An LLM can read the passages that the local model is least sure about. You set how much of each batch it may read. Entity types with properties go to the LLM, which fills in the values.
- The schema is part of the LLM prompt. BAML builds the allowed entity and relation labels from it, so the model can only return declared types, and validation removes anything else.
- Calls to an LLM work with many providers. Retries are built in, and fallback or rotation across several models is supported.
- You set separate confidence thresholds for each entity and relation type.
- Items that your schema does not allow are saved as candidates, with links to their source passages.
- You can list, search, approve, or reject candidates. Approving returns a schema patch for you to review, and your own schema file is never edited. Approved candidates then become entities, relations, or properties.

See [Extraction](../concepts/extraction.mdx), [Define a graph schema](../guides/define-a-graph-schema.mdx), [Choose an extraction mode](../guides/choose-an-extraction-mode.mdx), and [Review candidates](../guides/review-candidates.mdx).

## Entity resolution

<Diagram name="entity-resolution" ext="svg" alt="Extracted entities with the same label and text collapse into one entity. Other pairs go down tiers: a name gate, fuzzy match, embedding similarity, clustering, and LLM review. A match is stored as a link between entities, and linked entities are grouped under one resolved entity." />

- Entities with the same label and text are deduplicated into one entity, which records how often and where it appears.
- A name gate blocks pairs whose names carry different numbers, such as "Apollo 11" and "Apollo 13", and names that are very long.
- Similar spellings, close embeddings, and LLM-reviewed pairs are stored as links between entities. The original entities and their relations stay in the graph.
- Each connected set of matches is grouped under one combined entity that links to its members.
- A pair that no check can decide stays unmatched. It is never treated as a rejection.
- Only the hard pairs reach the LLM. The most similar unclear pairs go first, up to a limit that you set for each label.
- A graph-wide pass shows the matches it would make, and it writes them only when you ask.
- You can re-check the entities you name after new evidence arrives, or turn off a single match.
- When two entities disagree on a property, the first value is kept. Conflicting descriptions are summarized by an LLM, with a plain join as the fallback.
- After each job, new entities are compared with everything already stored. Two ingests that name one thing differently end up in one group.
- An entity and its matches are removed when an update, delete, or purge takes away the last evidence for it.

See [Entity resolution](../concepts/resolution.mdx) and [Consolidate duplicates](../guides/consolidate-duplicates.mdx).

## Communities

<Diagram name="community-detection" ext="svg" alt="Entities joined by relations weighted by their supporting passages are clustered with Leiden. Each community gets a report with a title, summary, and findings, and the report is embedded. A broad question is matched against the reports in theme search, which returns the passages behind each matching theme." />

- The entity graph is grouped into communities. You can preview the groups before writing them.
- Each relation is weighted by the number of passages that support it.
- An LLM writes a title, summary, rating, and findings for the larger communities. A simple template covers the rest.
- Each report is embedded, so `search_themes` can answer broad questions from the summaries and return the passages that support each theme.
- Thematic search matches a broad question against the embedded reports by meaning. It returns the matching themes with their entities and the passages that mention them, inside the documents in scope, and never the report text.
- Communities cluster the entities that your schema defines. Document structure, links to passages, and candidates are left out of the clustering.
- Writing communities replaces the earlier groups in one step, so a rerun is safe.

See [Communities](../concepts/communities.mdx).

## Keep the graph current

- Adding the same folder again refreshes the graph. Unchanged documents are skipped, and changed documents are replaced.
- A new version of a document is chunked and extracted again. When only extraction settings or descriptions change, the entities are extracted again and the chunks are kept. When only dates change, only the dates are written.
- You can delete a document to remove it from search while keeping its history. You can purge it to remove every version completely.
- Each document is written as one job with a lease. Nothing from a running job shows up in search until the job finishes.
- The next time a graph opens, it rolls back or finishes any job that a crash left behind.
- A status check tells you whether a document is current, pending, failed, deleted, or unknown.
- Each run returns counts for every stage, the failures with their details, and the true failure total. A progress callback receives a partial report after each batch of documents.

See [Ingestion](../concepts/ingestion.mdx) and [Update and delete documents](../guides/update-and-delete-documents.mdx).

## Keep the graph and its indexes in one database

- By default, the graph, its vector indexes, and its lexical indexes live in Neo4j or FalkorDB. You can instead keep vectors in one external store per graph: Qdrant, Milvus, or Weaviate. The graph database is always the source of truth. Both backends support ingestion, retrieval, conversation history, and decision traces. Compare their [search and transaction behavior](../concepts/graph-storage.mdx#choose-a-backend) and [configure either backend](../guides/configure-storage-backends.mdx).
- Writes go out in batches, and each failed record is reported by its identifier.
- Uniqueness constraints are created when a graph opens. Native vector indexes are created for graph-native placement, and lexical indexes are always created.
- The embedder is checked against the existing vector indexes before anything is written, so a mismatch is caught early.
- A local embedding model is used by default. An alternative is available as an optional part of the install.
- A node keeps its identity when its labels change.
- The database password is sent only over an encrypted connection when the host is remote.

See [Graph storage](../concepts/graph-storage.mdx).

## Search the graph and read the evidence

<Diagram name="search-evidence" alt="A query runs full-text, semantic, or hybrid search over the chunks of the documents you allow. Hits carry evidence ids, and a fetch returns the exact passage text with a citation. Optional steps navigate the document tree, search entities, and explore relationships." />

- Lexical search (BM25 full-text) matches keywords, semantic search compares embeddings, and hybrid search combines the two rankings.
- Results come from the current text of documents in the caller's scope. Older versions and rows from unfinished jobs stay out.
- Fetch returns the exact text behind a result. It says when the text was cut or covers only part of what was asked for.
- You can find entities by name and by embedding similarity, and see the passages that mention each one.
- You can walk outward from an entity a few steps. Relations that a passage supports are kept apart from bare connections.
- You can move from a passage to its parent section, its children, its siblings, the previous or next chunk, or the rows around a table cell.
- Failed search legs and cut-off results are reported, so an incomplete result is never mistaken for an empty one.
- Hybrid search reorders its top hits with a cross-encoder model when a reranker is configured.

[Retrieval](../concepts/retrieval.mdx) compares the strategies by mechanism and limit, the [tools reference](../reference/tools.mdx) lists every tool, and [Find and cite evidence](../guides/find-and-cite-evidence.mdx) calls them from Python.

## Cite a specific source version

- Each reference points to one version of one document.
- An older citation still resolves. It returns its text and is labeled as superseded.
- A check confirms that every cited passage was read in scope. It reports the passages that were not read, that belong to another document, or that are malformed.
- Answers are rendered with numbered references and a Sources list. A source becomes a link when it has a web address.

## Record conversation history

<Diagram name="conversation-history" alt="The agent records messages, tool calls, tool results, and named steps under a task. Decision traces cite document passages, task events, and earlier decisions. A source change flags affected decisions for review, and a later run can resume the task and search earlier decisions." />

- A task has a goal, ordered events, and named steps. Events include messages, tool calls, tool results, and notes.
- A step is not started, in progress, completed, failed, or unknown.
- A resumed task starts from a short summary: the goal, step counts, active decisions, and decisions that need review.
- Completed steps are reused. Steps that were still running are marked unknown.
- A repeated request ID returns the saved result for a completed write. Failed multi-statement writes on FalkorDB can leave partial effects that repeat on retry. See [retry limits](../guides/configure-storage-backends.mdx#retried-history-and-decision-writes).
- You can redact the body of one event, or delete a whole task with its events and steps.

## Record decision traces

- A decision stores a conclusion, a concise rationale, assumptions, and open questions. Decision traces are structured records.
- Supports can be document passages, task events, or other decisions.
- Replacing or rejecting a decision keeps the earlier record and its support history.
- When a cited document gets a new version or is removed, the decision is flagged with the reason.
- Decisions that depend on a flagged decision are flagged too, in small batches, so an interrupted review can continue.
- A decision is reaffirmed only after the current text of each cited document has been read.
- You can list choices that different tasks decided differently, and search earlier decisions in the same project.

See [Decision traces](../guides/decision-traces.mdx) to record supported decisions and review them when source documents change.

## Use the built-in agent

<Diagram name="full-flow" alt="Documents are loaded, chunked, extracted, and resolved into a graph with enterprise knowledge, conversation history, and decision traces. A changed document flags the decisions that cite it. An agent searches and reads the graph, records its events and steps, and returns an answer with checked numbered sources." />

- The agent is built for a fixed set of documents, a project, and an author, and it reads nothing else.
- Its evidence tools discover passages, find entities, explore relations, move between passages, and fetch exact text.
- A run ends as answered, short of evidence, partial, partially retrieved, out of budget, or unable to record its work.
- Citations are checked against passages read in the same run, and the agent gets one repair pass.
- Its messages, tool calls, and results are saved to the task log as the run goes.
- You set how many steps and tool calls a run may use.
- You can use one model, a fallback chain, or a rotation across Anthropic, OpenAI, OpenAI-compatible, and Google models.

See [Agent loop](../concepts/agent-loop.mdx).

## Work with any MCP client

- One command starts a local server that talks to your MCP client over standard input and output.
- Search, exact fetch, navigation, entity search, relation exploration, and citation checks are separate tools.
- The conversation history and decision tools read and write task events, steps, and decisions in a configured project.
- Writing is off by default. The operator switches it on, and rejecting a decision has its own switch.
- The documents and the project come from the server configuration, and a tool call cannot change them.
- A decision can cite only evidence that the same server process fetched in full.
- Each result has a size limit and a deadline, and the server reports what it left out.
- A client can reuse a request identifier when it retries a write.

See [Run the MCP server](../guides/run-the-mcp-server.mdx).

## Show what happened

- Pass an OpenTelemetry tracer to the graph, the agent, the stores, the embedders, and the extractors. Without a tracer, nothing is recorded.
- Spans cover loading, chunking, extraction, resolution, merging, storage, search, and LLM calls, including each attempt and its token counts.
- Tool and model calls in an agent run appear under your active span.
- Each failure record carries the trace and span it came from.
- Entities and relations that were dropped are counted by kind, label, and reason.

See [Observability](../concepts/observability.mdx) and [Trace spans](../reference/trace-spans.mdx).

## Measure quality on your own data

- Answer scores cover correctness, faithfulness, context precision, context recall, and citation accuracy. A judge model that you choose computes them.
- Each cited sentence is checked against the evidence that sentence cites.
- Extraction is scored against hand-written answers, and duplicate groups are scored with standard clustering measures.
- Agent runs can be scored from their traces.
- A ready-made script runs the answer scores on your own documents and questions, and prints a table of results.

See [Score on your own questions](../guides/score-agrag-on-your-questions.mdx).

## Fit your setup

- Every component reads its settings from environment variables or a file, with a prefix for each area.
- Point extraction, the agent, and the judge at one OpenAI-compatible endpoint, or give each its own.
- Stored fingerprints of the schema and the extraction settings decide whether an update chunks again, extracts again, or skips the work.
- You can install only the optional parts you use. They cover storage, local extraction, LLM calls, the agent, the MCP server, PDF reading, communities, tracing, and evaluation.

See [Installation](./installation.mdx) and [Configuration](../reference/configuration.mdx).
