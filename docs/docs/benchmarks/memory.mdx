# Memory benchmark

This page describes the Memory benchmark: the questions, the graph schema, how `agrag` answers are scored, and the result of the committed lite run. For the commands, see [Run the benchmarks](./run-benchmarks.mdx). For the audit trail and the limits of these numbers, see [Benchmarks](./index.mdx).

## The dataset

[BEAM](https://github.com/mohammadtavakoli78/BEAM) ([paper](https://arxiv.org/abs/2510.27246)) tests memory over a long chat between a user and an assistant. Each conversation has many sessions, and each session has many messages. After the chat, the benchmark asks probing questions about it. Each question has a rubric: a list of facts that a correct answer must state.

The harness reads the 100K-token split of the dataset [`Mohammadta/BEAM`](https://huggingface.co/datasets/Mohammadta/BEAM) at a pinned revision. It checks the hash of the file before it uses it. It ingests the chat only. The plan, the profile, and the reference answers that the dataset holds beside the chat never reach `agrag`.

One assistant message in conversation 4 turned into 345,211 spaces of filler. The harness cuts that message after its last sound text and adds a short marker. It checks the hash of the original first.

The probing questions fall into ten abilities:

| Ability | What the question asks |
|---|---|
| `abstention` | A fact that the chat never states. The right answer says so. |
| `contradiction_resolution` | A point where two statements of the user disagree. |
| `event_ordering` | The order of events in the chat. |
| `information_extraction` | One fact from the chat. |
| `instruction_following` | A request that must follow an earlier standing rule of the user. |
| `knowledge_update` | A fact that the user changed during the chat. |
| `multi_session_reasoning` | An answer that joins facts from several sessions. |
| `preference_following` | A request where an earlier preference of the user should shape the answer. |
| `summarization` | A summary of a part of the chat. |
| `temporal_reasoning` | A question about time between events. |

### Lite and full

| Set | Questions | Conversations | Tokens |
|---|---|---|---|
| Lite | 10, one for each ability | 1 (`conv17`) | 124,033 |
| Full | 100, ten for each ability | 5 (`conv1`, `conv4`, `conv6`, `conv13`, `conv17`) | not measured here |

Every lite question is also in the full set. Each conversation gets its own Neo4j service and its own graph. A question about one conversation cannot find text from another. Each session of a conversation is one document.

Four questions of the full set have a known defect in their rubric. They carry the flag `known_bad_rubric`. The lite set has none.

## The graph schema

See `benchmarks/schemas/memory.py`. The schema has these entity types: `Person`, `Place`, `Organization`, `Tool`, `Topic`, `Event`, `Fact`, `Instruction`, `Preference`, `Measure`, and `Session`.

A statement is a node, not a relation, because a relation carries no time and no order. A newer `Fact` `SUPERSEDES` an older one. Two opposing facts stay linked by `CONTRADICTS`. A standing rule (`Instruction` or `Preference`) points at the topic that triggers it. A `Session` node holds the only clock: one date for each session. The order of messages comes from the order of the chunks.

A schema that fits the corpus helps `agrag`, so these numbers do not compare with systems that use another schema.

## How answers are scored

A judge model reads the answer and the rubric. It scores each rubric item 1, 0.5, or 0. The score of a question is the mean of its item scores. The score of an ability is the mean over its questions.

Each question gets these metrics:

- **`score`.** The score of the question.
- **`score_excluding_known_bad`.** The same score, except that a question with the flag `known_bad_rubric` has no value. The group mean therefore leaves it out.
- **`event_f1` and `event_tau_norm`.** For `event_ordering` only. The harness splits the answer into lines and matches them to the rubric items. `event_f1` is the F1 of that match. `event_tau_norm` is the normalized rank correlation of the two orders. The `score` of the question is `event_f1` times `event_tau_norm`.

The scorer is ported from the benchmark, with its prompts kept. The judge is the judge model of the run. A judge reply that does not parse scores 0 for its item, and the question gets the flag `parse_error`.

The benchmark reports only the rank correlation for event ordering. Its `score` is stricter, so do not compare it with a published event ordering number.

The judge is the same model as the agent by default, so the scores are biased upward. See [Benchmarks](./index.mdx#who-grades-the-answers).

## Results of the lite run

The run used `gemma4:31b` for extraction, the agent, and the judge, on one clean commit, with the default chunking of about 1,000 tokens.

| Ability | Questions | `score` |
|---|---|---|
| All | 10 | 0.70 |
| `abstention` | 1 | 1.00 |
| `contradiction_resolution` | 1 | 0.75 |
| `event_ordering` | 1 | 0.13 (`event_f1` 0.33, `event_tau_norm` 0.40) |
| `information_extraction` | 1 | 1.00 |
| `instruction_following` | 1 | 0.00 |
| `knowledge_update` | 1 | 1.00 |
| `multi_session_reasoning` | 1 | 1.00 |
| `preference_following` | 1 | 1.00 |
| `summarization` | 1 | 0.10 |
| `temporal_reasoning` | 1 | 1.00 |

Each ability has one question, so each row is one answer. One question moves the mean by 0.1. A lite run shows that the pipeline works. It does not rank systems or abilities.

No question failed, and no question carries a flag. The agent answered the `preference_following` question with one model call and no retrieval, so that score does not test the graph.

The graph has 644 entities and 276 relations from 128 chunks. Four chunks gave an empty extraction. 142 of the relations are `PART_OF`.

Print the record with:

```bash
uv run python -m benchmarks report --domain memory
```

## Cost and time

| Phase | Model calls | Tokens |
|---|---|---|
| Ingest | 847 | 12.5M |
| Agent, 10 questions | 134 | 0.77M |
| Judge, 10 questions | 37 | 0.026M |
| Total | 1,018 | 13.3M |

The run took about 115 minutes. Ingest used 83% of the calls and 94% of the tokens. Extraction took 128 calls, one for each chunk. The other 719 ingest calls resolve duplicate entities and merge them. In the run, `agrag` dropped some pairs of entities at its limit on resolution calls, so the graph can keep a few duplicates.

The dry-run estimate for this run was about 1,600 calls and 16.1M tokens. The run used fewer of both. The estimate is not an upper bound, so the spend caps are 1.5 times the estimate: 2,400 calls and 24.2M tokens for lite, and 16,400 calls and 132.7M tokens for full. Nobody has measured a full run. Run `make bench-dry DOMAIN=memory MODE=full` and read the estimate before you start one.
