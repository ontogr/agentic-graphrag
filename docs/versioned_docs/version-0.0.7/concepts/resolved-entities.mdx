# Matching and resolved entities

When resolution decides that entities match, Agentic GraphRAG records the decision and derives a resolved entity for the connected group. The original entities and their relations stay in the graph, so a match can be reconsidered without reconstructing discarded facts.

## Why it exists

A merge that rewrites or deletes nodes is hard to undo. A later run can learn that two names belong to two different people. If the nodes were merged, their facts are already mixed.

For a judgment call, Agentic GraphRAG adds a link rather than rewriting an entity. It derives one summary node from the linked group, while each link retains its decision evidence. A later re-evaluation can deactivate a link. The cost of this reversible model is extra nodes and edges, and relations remain on member entities rather than moving to the summary.

Exact matches are the one exception. Two extracted entities with the same label and the same normalized text are the same entity from the start. They share one node. The node counts the extracted entities it received and lists every source chunk.

## How it works

<Diagram folder="docs" name="resolved-entities" alt="Three entities that name the same person are joined by MATCHES links. Each entity has a RESOLVED_AS link to one ResolvedEntity that groups them. No entity changes, and the relations stay on the members." />

*A match adds links and one derived node. It changes no existing entity.*

1. Resolution confirms that two entities match. It records the tier, the score when one exists, and the reason when an LLM decided.
2. A `MATCHES` edge is written between the two `Entity` nodes. The edge keeps that record and the time of the decision.
3. The connected group is collected. If A matches B and B matches C, then A, B, and C are one group.
4. One `ResolvedEntity` is computed for the group. The next section explains how.
5. The `ResolvedEntity` node is written, with one `RESOLVED_AS` edge from each member to it.
6. Retrieval can search resolved entities. The relations of a member do not move; they stay on the member.

## How the group gets its name and properties

Agentic GraphRAG reads members in an order based on their ids and keeps the first value it sees for each property, including the name. This rule makes recomputation from the same stored members repeatable, but it does not select the clearest name. Separate ingests can produce different names because their entity ids can differ.

For the description, Agentic GraphRAG asks an LLM to write one summary of all different descriptions. If no LLM is available, or the call fails, Agentic GraphRAG joins the descriptions with " | ". No description is dropped.

## Example

Three entities come from three documents: "Babbage Charles", "Charles Babbage", and "C. Babbage".

| Link | Deciding tier |
| --- | --- |
| Babbage Charles and Charles Babbage | Fuzzy, score 1.0 |
| C. Babbage and the other two | LLM |

The result is one `ResolvedEntity` with three `RESOLVED_AS` edges. In one test run its name was "Babbage Charles". In another run over the same text it was "Charles Babbage", because entity ids differ between ingests.

<details>
<summary>Design choices</summary>

Agentic GraphRAG does not rewrite or delete the nodes, so a wrong match needs no repair. The original entities and their relations are still there.

The node is derived rather than picked as a winner, because no member is the truth. The group can grow or shrink when a link changes, and Agentic GraphRAG recomputes the node from the current members each time.

Each `MATCHES` link keeps its tier, score, and reason, so you can audit a match.

The name comes from a fixed order, so the same members give the same name each time the node is recomputed. It is not chosen as the best name. If a name matters to you, read the members and choose one in your own code.

Extracted entities with equal normalized text share one node because there is nothing to judge, and nothing to undo.

</details>
