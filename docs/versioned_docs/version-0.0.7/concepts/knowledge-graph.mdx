# Knowledge graph

The knowledge graph stores source structure, searchable chunks, extracted entities, and links between them in the graph database. This lets retrieval move from a match to related facts and back to the text that supports them.

## Why it exists

Every fact in an answer must trace back to text. A graph of only entities cannot show where a fact came from. A graph of only text cannot connect facts.

Agentic GraphRAG keeps both text and structure in one graph. An entity links to the chunks that mention it, and a chunk links to its document and sections. Retrieval can therefore use relationships without losing the path back to source evidence.

## How it works

*The node kinds and their edges. Entity nodes use your schema's type names as labels. `HAS_PART` also joins a document to each section, table and figure.*

1. Document: one node for each logical document. Its `document_key` stays the same when the content changes. It holds the source location, the title, the current content hash, optional `published_at` and `content_date` dates, and the name, version and fingerprints of the schema and extraction setup that produced it.
2. Section: one heading of a document, or the unheaded content when the document has no headings yet. It holds the heading, its depth, and its page range or character range. It holds no text. The chunks under it hold the text. A section has a stable `section_key` that stays the same while the heading path and the place among sections with that path stay the same.
3. Table and Figure: one node for each table or figure. A table holds its caption, its column names and its row count. A figure holds its caption and its page box. It does not store the image.
4. Source: one node for each record file, such as a CSV file. It joins each of its row documents with `HAS_DOCUMENT`.
5. Chunk: one retrieval-sized piece of text. It holds the text, its location in the source, the headings above it, the sections it covers and the chunker that made it.
6. Entity: one node for each name and type, such as the person "Ada Lovelace". Its label is the type from your schema. A type with parents also adds the labels of its parents to the node. The same name with two types makes two entities. It records which chunks mention it. A schema cannot use these graph-owned labels as an entity type or a parent type: `Document`, `Chunk`, `Section`, `Table`, `Figure`, `Source`, `Community`, `ResolvedEntity`, `CutoverJob`, `Candidate`, `VectorPlacement`, `_Node`, and `_MergeAlias`.
7. ResolvedEntity (see [Matching and resolved entities](./resolved-entities.mdx)): a group of entities that the resolver decided are the same thing. It exists only for groups of two or more.
8. Community (see [Communities](./communities.mdx)): a group of related entities. It holds a title, a summary, a rating and findings.

The nodes form a tree. A document holds its top-level sections, and each section nests under the nearest heading above it with a smaller depth. A section holds the chunks, tables, and figures that it contains, in reading order, and a table holds the chunks of its row groups.

The edges connect them:

- `HAS_CHILD` builds the tree. It joins a document or section to its sections, tables, figures and chunks, and a table to its chunks. It carries an `order`, the reading order of the child.
- `HAS_DOCUMENT` joins the source file of a record file, such as a CSV file, to each of its row documents.
- `HAS_PART` joins a document to each of its sections, tables, figures and chunks. It records `valid_at` and `invalid_at` timestamps. The edge is open while `invalid_at` is null and the node belongs to the current version of the document. `HAS_CHILD` gives the reading order. `HAS_PART` says which document version owns a node.
- `NEXT_CHUNK` joins two neighbouring chunks of one document.
- `MENTIONED_IN` joins a chunk to each entity it mentions.
- A schema relation joins two entities, for example `WORKED_WITH`. Only the patterns that your schema allows can exist.
- `MATCHES` joins two entities that the resolver matched. See [Matching and resolved entities](./resolved-entities.mdx).
- `RESOLVED_AS` joins an entity to its resolved entity.
- `MEMBER_OF` joins an entity to its community.

### Conversation history and decision traces

Conversation history and decision traces live in the same graph as source documents. A task has `HAS_EVENT` edges to its ordered events and `HAS_STEP` edges to its named steps. Events include messages, tool calls, and tool results. A task has `MADE` edges to its decisions. A decision has `HAS_SUPPORT` edges to its supports, and `DEPENDS_ON` and `SUPERSEDES` edges to other decisions. A document support identifies a document version and a chunk or character span, so it points to the same text after the document changes. Decision records hold explicit supports and a concise rationale.

## Example

Take a note with two sentences about Ada Lovelace, Charles Babbage and the Analytical Engine. With `DEFAULT_SCHEMA`, one run writes the document, the section, the chunk, one entity node for each distinct person, place, product or event it finds, and a relation edge when the text states one of the eight relations. A schema for your domain gives the extractor more specific targets.

<details>
<summary>Design choices</summary>

Chunks are nodes so that an answer can cite its source, and so that a search can step from one chunk to its neighbours.

`HAS_PART` has an end time instead of being deleted. A changed document closes its old edges and opens new ones, and the old chunks stay as history. Search reads only open edges, so a removed document leaves retrieval at once.

The resolver adds a ResolvedEntity instead of merging entities, because a match is a judgement. The original entity nodes stay, so a wrong match loses no information.

The type is the label, because the type is what you filter and index by. A parent type is a label too, so a filter on `Organization` returns `Vendor` entities. Every Agentic GraphRAG node also carries an internal marker label, so Agentic GraphRAG can find its own nodes in a shared database.

A chunk can span several sections, so it stores their ids in `section_ids` instead of as edges. A reader can find them without a traversal. The [Chunking](./chunking.mdx) page explains how a chunk records its sections.

</details>
